# Network and ISP Restrictions

## 1. Overview

ISP interference affected access to the examination infrastructure during the early stages of the examination.

Two workarounds were used:

1. A browser VPN was used to access the examination website and continue the initial attacks.
    
2. Windscribe was subsequently installed inside Kali to provide VPN connectivity for terminal-based tools.
    

The underlying problem was that browser VPN traffic and Kali terminal traffic followed different network paths.

## 2. ISP Interception — HTTP Redirection

During ME-01, a request to the examination server using `curl` returned:

```
HTTP/1.1 307 Temporary Redirect
Via: 1.0 middlebox
Location: http://megaplusredirection.tedata.net/VDSL-Redirection_100.html
Connection: close
```

This was not the expected response from the Academy application.

The `Via: 1.0 middlebox` header and redirection destination indicated that an intermediary was intercepting the request and redirecting it to an ISP VDSL redirection page.

The examination endpoint was using HTTP rather than HTTPS. The request therefore travelled without TLS protection, allowing an intermediary on the network path to inspect and redirect it.

**Finding:** ISP-level HTTP interception was directly observed.

## 3. Initial Workaround — Browser VPN

The browser VPN successfully provided access to the examination website.

It allowed the browser to reach the target through the VPN instead of relying on the normal ISP route.

However, it did not automatically tunnel traffic generated by Kali's terminal.

This created an important limitation:

|Tool|Network path|
|---|---|
|Browser with VPN extension|Browser VPN|
|Kali `curl`|Normal Kali routing|
|Kali Nmap|Normal Kali routing|
|Kali Python requests|Normal Kali routing|

This is why the website could work in the browser while the same endpoint returned an ISP redirect through `curl`.

The browser VPN was sufficient as an initial workaround, but it was not a complete solution for the examination workflow.

## 4. Root Cause Investigation — Kali Routing

The following command was executed:

```
ip route get x.x.x.x
```

Observed output:

```
x.x.x.x via 192.168.73.2 dev eth0 src 192.168.73.130 uid 1000
```

This established that traffic to the public examination address was leaving through:

|Field|Value|
|---|---|
|Destination|`x.x.x.x`|
|Gateway|`192.168.73.2`|
|Interface|`eth0`|
|Source address|`192.168.73.130`|

The Academy OpenVPN connection was already active through `tun0`.

However, its routing table contained specific private lab networks rather than a default route for all internet traffic.

Examples:

```
10.10.8.0/22
10.10.16.0/23
10.10.110.0/24
10.13.37.0/24
10.13.38.0/24
10.129.0.0/16
```

Consequently:

- Academy private networks used `tun0`.
    
- General internet traffic used `eth0`.
    
- The public examination endpoint was reached through `eth0`.
    
- The ISP could therefore intercept the HTTP request despite Academy OpenVPN being connected.
    

**Key lesson:** An active VPN connection does not mean all system traffic is routed through that VPN. Always inspect the actual route to understand which interface carries a request.

## 5. Second Workaround — Windscribe on Kali

A browser-only VPN was insufficient for the terminal-based workflow.

Windscribe was selected because an account was already available and a Linux desktop client was offered.

### Installation obstacles

The first download attempt produced an unexpected result:

```
windscribe.deb: HTML document, Unicode text, UTF-8 text
```

`dpkg-deb` consequently rejected the file because it was not a Debian package.

The mistake was assuming that a `.deb` filename guaranteed that the downloaded content was actually a Debian package.

The correct AMD64 Debian package was subsequently obtained and verified.

The examination record confirms:

```
Debian binary package (format 2.0)
```

Its SHA-256 check returned:

```
windscribe_2.24.13_amd64.deb: OK
```

APT's installation simulation showed that only Windscribe and one additional dependency would be installed, without removing or upgrading existing packages.

### VPN coexistence

The Academy OpenVPN connection was configured as a split tunnel.

The intended arrangement was:

|Component|Intended network path|
|---|---|
|Windscribe-selected applications|Windscribe|
|Academy private lab networks|Academy OpenVPN (`tun0`)|
|Other applications|Normal system routing|

Instead of replacing the Academy VPN or forcing Windscribe to become the global default route, the selected approach was Windscribe's inclusive split tunneling.

The intended application selection was:

```
/usr/bin/curl
```

This allowed terminal HTTP requests to use Windscribe while preserving the Academy VPN configuration.

No static route tied to an individual examination IP was required. The public server address could change between instances.

### Successful connectivity test

After the workaround, the same ME-01 endpoint returned:

```
HTTP/1.1 200 OK
Server: gunicorn
Connection: close
Content-Type: application/octet-stream
Content-Length: 161
```

The expected file-share response followed.

This confirmed that the request was reaching the application rather than being redirected to the ISP's VDSL page.

## 6. Separate Incident — IN-01 HTTP Timeouts

During IN-01, another connectivity issue occurred.

A request returned:

```
curl: (28) Operation timed out after 12002 milliseconds with 0 bytes received

HTTP: 000
Connect: 0.248585s
First byte: 0.000000s
Total: 12.002333s
```

Unlike the earlier ISP redirection, this request established a TCP connection but did not receive an HTTP response before the timeout.

The public endpoint later recovered.

The available evidence does not establish whether this particular timeout originated from the ISP, target application, or hosting infrastructure.

Keep this incident separate from the confirmed ISP middlebox redirection.

## 7. Lessons Learned

1. Browser VPN extensions do not automatically protect terminal traffic.
    
2. An active Academy VPN does not necessarily route general internet traffic.
    
3. `ip route get` is useful for identifying the actual outgoing interface for a destination.
    
4. HTTP traffic can be intercepted and redirected by an intermediary on the network path.
    
5. A system VPN or application-level split tunnel is more suitable when terminal tools require VPN connectivity.
    
6. Multiple VPN clients can introduce routing and firewall conflicts; preserve the working Academy connection.
    
7. Never assume a downloaded package is valid based on its filename. Verify its actual file type.
    
8. Avoid static routes tied to disposable examination target addresses.
    
9. Do not confuse a TCP connection timeout, an HTTP read timeout, and an ISP-generated HTTP redirect. They are different failure conditions.
